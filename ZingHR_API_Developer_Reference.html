ZingHR API — Developer Reference

Complete reference for the ZingHR integration in app/integrations/zinghr.py — RDC Teamlease Onboarding Portal.

Generated 2026-09-15 from the live source. Line numbers reference app/integrations/zinghr.py as of this date.

No credentials embedded. This file has no API keys in it — the real ZINGHR_CLIENT_ID / ZINGHR_CLIENT_SECRET live only in your local .env file (gitignored). Every example below uses placeholders you fill in yourself from there.

1. Credentials

Two values, both in your project's .env file (never in source code — see app/integrations/zinghr.py lines 19-20):

Env varUsed as
ZINGHR_CLIENT_IDHTTP Basic Auth username
ZINGHR_CLIENT_SECRETHTTP Basic Auth password

Open your local .env and copy these two values out for the commands below — do not paste them into this file or anywhere shared.

2. Step 1 — get an access token

GEThttps://mservices.zinghr.com/etl/api/v2/Auth/GenerateJWTToken?apiPermission=GEMD

Auth: HTTP Basic, username = ZINGHR_CLIENT_ID, password = ZINGHR_CLIENT_SECRET. No request body.

curl -u "<ZINGHR_CLIENT_ID>:<ZINGHR_CLIENT_SECRET>" \
  "https://mservices.zinghr.com/etl/api/v2/Auth/GenerateJWTToken?apiPermission=GEMD"

Response shape:

{ "data": "<bearer-token-string>", ... }

Save that token string — you'll pass it as Authorization: Bearer <token> on every call below. The app does not cache this token long-term; request a fresh one per session (zinghr.py line 33).

3. Step 2 — fetch employees

POSThttps://mservices.zinghr.com/etl/api/v2/Employee/GetEmployeeDetails 
curl -X POST "https://mservices.zinghr.com/etl/api/v2/Employee/GetEmployeeDetails" \
  -H "Authorization: Bearer <token-from-step-1>" \
  -H "Content-Type: application/json" \
  -d '{"Pagesize": "500", "Pagenumber": "1", "employmentstatus": "Active"}'
Body fieldMeaning
PagesizeRows per page. The app uses 500 (zinghr.py line 22).
Pagenumber1-indexed page to fetch.
employmentstatus"Active" — server-side filter. This is the only status filter the ZingHR API itself supports; there's no separate "all employees" call.

Response shape:

{
  "data": {
    "employees": [ { ...one raw employee record, see section 5... }, ... ],
    "employeesCount": 500
  }
}

4. Pagination

1Start at Pagenumber=1.
2If data.employees is a non-empty list, collect it and request Pagenumber+1.
3Stop as soon as a page comes back with an empty employees list.

The app also hard-stops after page 20 as a safety cap (zinghr.py line 110) — well beyond any realistic page count at ~1,280 active employees / 500 per page (3 pages in practice). No delay is required between pages (unlike Truein, ZingHR isn't rate-limited the same way) — the app fires each page request immediately after the previous one returns.

5. The attributes[] array — how Location/Company/etc. actually arrive

Each raw employee record looks like this:

{
  "employeeCode": "0001",
  "employeeName": "SUBBARAO C V  ",
  "email": "Robo@zinghr.com",
  "mobileNo": "",
  "gender": "Male",
  "dateOfBirth": "01 Jan 1982",
  "dateOfJoining": "12 May 2000",
  "dateOfLeaving": "",
  "employeeStatus": "Existing",
  "addresses": [ {"city": ""}, {"city": ""}, {"city": ""} ],
  "attributes": [
    {
      "attributeTypeDescription": "Company",
      "attributeTypeUnitDescription": "Robo Silicon Pvt. Ltd.",
      "attributeTypeID": 40,
      "attributeTypeUnitID": 2298,
      "attributeTypeCode": "Company",
      "attributeTypeUnitCode": "ROBOSilico"
    }
  ]
}

Critical thing to understand: attributes is a sparse list — it only contains an entry for whichever attribute types ZingHR actually has data for on that specific employee. There's no fixed schema forcing every attribute to appear. The app builds a lookup dict keyed by attributeTypeCode (zinghr.py line 50) and reads six of them:

City
Company
Cost Center
Department
Designation
Location

If an attributeTypeCode is simply missing from an employee's attributes array — as in the example above, which has only "Company" — the app reads it as an empty string, because there is nothing there to read. This is not a parsing bug; it's the literal content ZingHR returned for that employee. The only way to independently confirm this for any employee is to look at their raw attributes array yourself, exactly as in the example above — if you only see a Company entry and nothing else, that's ZingHR's own data, not this app's interpretation of it.

6. Worked example — checking one employee's raw record

To check whether a specific employee (say, ROBO employee code 0001) really has no Location on file:

1Run the Step 1 auth call, get a token.
2Run the Step 2 employees call for each page (1, 2, 3, ...) until a page comes back empty.
3In the combined JSON, find the object where "employeeCode": "0001".
4Look at that object's attributes array. Count how many entries it has and what each one's attributeTypeCode is.

Tip: pipe the response through jq to jump straight to one employee, e.g.:

curl ... | jq '.data.employees[] | select(.employeeCode == "0001")'

7. Company values (RDC / Robo / Ultrafine)

ZingHR is one shared tenant across all three companies — there's no server-side company filter on the employees endpoint. Every record carries its company in the Company attribute's attributeTypeUnitDescription. Exact strings currently in use (case-sensitive as ZingHR returns them):

Raw valueMeaning
RDC Concrete India Ltd.RDC
Robo Silicon Pvt. Ltd.ROBO
Ultrafine Mineral and Admixtures Pvt LtdUltrafine
CommonUnclassified — 1 record seen, not attributable to any single company
(blank / attribute missing)Unclassified — kept as RDC by the main pipeline (can't confirm it's not RDC), excluded by the Robo/Ultrafine snapshot (can't confirm it is one of them either)

The app matches these case-insensitively and lowercased (see _NON_RDC_COMPANIES / _ZINGHR_COMPANY_TO_CODE in app/services/headcount.py) — but the raw values above are exactly what the API returns.

8. Known quirks

QuirkDetail
Duplicate employeeCodesA small number of employees appear twice in the raw pages — once with a full attributes array, once with it empty/missing. The app keeps whichever copy has more attributes (_dedupe_by_employee_code(), zinghr.py line 61) and discards the thinner one.
Face-attendance pseudo-employeesRecords like employeeCode="FACEBACHUPALLY", employeeName="Face HYD Bachupally" are attendance-device registrations, not real people — filtered out by checking whether "face" appears in either field (case-insensitive).
1-hour cache, per processThe running app caches the full employee pull for 1 hour in a module-level variable. A fresh script (like the curl commands above, or a standalone Python script) always starts cold — it will never see the running server's cached copy, and vice versa.
No live company filterThere's no request parameter to ask the API for only one company's employees — you always get everyone active across RDC/Robo/Ultrafine/Common/blank in one pull, and filter client-side afterward.

9. Postman alternative

If you'd rather use Postman than curl: create a GET request to the Step 1 URL with Basic Auth (username/password = your two env var values) to get the token, then a POST request to the Step 2 URL with an Authorization: Bearer header and the JSON body from section 3. No Postman collection file is checked into this repo for ZingHR (unlike Truein's) — the two requests above are the entire surface area.
