venv\Scripts\python run.py

# Run with debug mode

venv\Scripts\pip install -r requirements.txt

venv\Scripts\python -m pytest

DVT_BASE_URL / DVT_USERNAME / DVT_PASSWORD                         # mandatory for the RDC staffing-norms volume pull

**Changed 2026-09-15**: these 8 integration credentials used to have real values hardcoded as fallbacks directly in `app/integrations/{truein,zinghr,dvt}.py` (`os.environ.get("X", "<real-value>")`) so the app worked even with an empty `.env`. As part of setting this project up as a git repo, all 8 fallbacks were removed (`os.environ.get("X")`, no default) so a real secret can never end up in git history again. **This means `.env` is no longer optional for these three integrations** — a fresh clone/environment without a populated `.env` will get `None`/empty-string credentials and every Truein/ZingHR/DVT call will fail (401/auth error), not silently fall back to a working value like it used to. Ask whoever manages those accounts for the real values (see `.env.example` for the exact variable names).

## Architecture

### Application factory
`app/__init__.py` — `create_app()` wires all Flask extensions, registers the 6 blueprints, adds session-timeout and security-header middleware, and calls `_auto_migrate()` on startup. `_auto_migrate()` adds missing columns/indexes to existing MySQL DBs and is safe to run repeatedly. New columns go in the `_REQUIRED_COLUMNS` list there.

### Blueprint layout
| Blueprint | URL prefix | Responsibility |
|---|---|---|
| `auth_bp` | `/auth` | Login, logout, forgot/reset password |
| `main_bp` | `/` | Role-aware dashboard, notifications |
| `requests_bp` | `/requests` | Full onboarding request lifecycle |
| `admin_bp` | `/admin` | Users, plants, designations, form fields, audit log, Truein dry-run |
| `exports_bp` | `/exports` | Filterable Excel report (preview + download) |
| `profile_bp` | `/profile` | Self-service profile, avatar, password change |

### State machine (`app/utils.py`)
The entire approval workflow lives in the `TRANSITIONS` dict — a flat map of `(current_status, actor_role, action) → new_status` — plus two conditional branch points in `get_new_status(req, actor_role, action)` that key off `req.is_special_case`. Exactly two paths exist:

- **Standard:** `DRAFT → PENDING_BH → PENDING_HR_MANAGER → PENDING_HEAD_HR → ACTIVE`
- **Over-norm ("special case"):** `DRAFT → PENDING_BH → PENDING_HEAD_HR → PENDING_DR_BHOON → ACTIVE` (skips HR Manager). Entered when the RDC staffing gate blocks a hire and the initiator acknowledges proceeding anyway (`is_special_case = True`, set via the form popup or the Submit-time fallback page) — see the RDC Staffing Norms section. Every approver in this chain must write a justification of at least 20 characters (vs. 5 for standard approvals).
- **Rejection:** Any `PENDING_X → REJECTED_X`; initiator resubmits back to `PENDING_BH`

`get_new_status()` performs the lookup (raises `ValueError` on invalid transitions). `can_act_on()` gates approver access, including BH-to-initiator scoping.

**Removed (2026-09-03):** a third, independent path used to let a Business Head manually flag any `PENDING_BH` request straight to Dr. Bhoon, skipping HR Manager *and* Head HR entirely (`flag_special()` route, `ApprovalActionType.FLAGGED_SPECIAL`, the "Flag for Dr. Bhoon" button on the request detail page). This was removed at the stakeholder's explicit request — only the two flows above should exist. `ApprovalActionType.FLAGGED_SPECIAL` and the `BH_BYPASS` branch in `view_request()`'s workflow-map builder (`app/requests_bp/routes.py`) were deliberately left in place, unused by any reachable code path, purely so the workflow map still renders correctly for the one real historical request that went through this path before removal — do not reintroduce the route/button when touching this area.

### Key models (`app/models.py`)
- **`OnboardingRequest`** — form responses stored as JSON in `_form_data` (use the `form_data` property). Four denormalized columns (`candidate_name`, `designation`, `plant_location`, `company_code`) are synced via `_sync_quick_access()` for fast list queries. URLs use `public_token` (UUID4 hex) — never expose integer IDs.
- **`User`** — `business_head_id` (self-referential FK) is **legacy/unused** (see gotcha below). Has `failed_login_attempts`/`locked_until` columns, but lockout enforcement itself was removed 2026-09-03 — failed logins are logged only, never counted toward locking the account.
- **`InitiatorRegion`** / **`BusinessHeadRegion`** — many-to-many Initiator↔region and BusinessHead↔region junction tables (both via `ClusterNameMapping`). Both roles can have multiple regions. This is the **sole** routing mechanism for which Business Head(s) see/can act on an Initiator's requests — see gotcha below.
- **`FormField`** — admin-configurable, 3-step dynamic form schema. Supports inline options, designation lookup, plant lookup. Drag-reorderable.
- **`AuditLog`** — append-only. Written via `log_audit()` in `app/utils.py`; never committed inside that function — always committed atomically by the caller.

### Critical patterns

**Soft-delete everywhere** — `PlantLocation`, `Designation`, `FormField`, `OnboardingRequest` use `is_deleted=True`. All queries must filter `.filter_by(is_deleted=False)`.

**Initiator ↔ Business Head routing is purely region-overlap based (redesigned 2026-09-04).** `app/utils.py::bh_ids_for_initiator(initiator)` returns every active Business Head who shares **at least one** region with the initiator (`InitiatorRegion` ∩ `BusinessHeadRegion` on `cluster_id`) — both sides can have multiple regions, and any overlap is enough. Returns `None` ("unscoped — every active BH can see/act on it") when the initiator has no regions at all, or none of their regions are actively covered by any BH — a request must always be reachable by someone rather than going nowhere. This same function backs `can_act_on()` (approval gating), `_get_bh_recipients()` (submit notifications), and `main.dashboard()`'s BH queue scoping (`app/main/routes.py`) — all three must stay in sync with this priority/fail-open logic if touched.
**`User.business_head_id` is legacy and unused by any reachable code path** — the old direct Initiator→one-Business-Head assignment (with its raw-SQL-update-to-bypass-enum-caching quirk) was fully replaced by region-based routing. The admin UI no longer exposes a way to set it (`new_user()`/`edit_user()` in `app/admin/routes.py` don't read or write it), and it's left in place, unused, purely to avoid a destructive column drop on live data (same convention as `StaffingGateCheck.overridden_*`) — do not reintroduce a "pick one Business Head" dropdown when touching this area. If you see it referenced in old data (a pre-2026-09-04 audit log entry, say), it's historical only.

**Audit logging** — call `log_audit(category, action_type, ...)` before `db.session.commit()`. The row is staged in the session and flushed atomically with the action.

**File uploads** — saved to `app/static/uploads/` with UUID-prefixed names. Always run `validate_mime()` (magic-byte check) in addition to extension checking.

**Email is async** — `send_email()` spawns a daemon thread. If `MAIL_USERNAME` is unset, it skips silently (good for local dev).

**Per-user email notification preferences (added 2026-09-10).** `User.email_mode` (`"ALL"`/`"HIRING_ONLY"`) and `User.daily_digest_enabled` (independent add-on, not a third mode) are set from Profile → Email Notifications. `notify_users(db, request_obj, recipients, subject, body, category="HIRING")` in `app/utils.py` always creates the in-app `Notification` row regardless of preference — only the outbound email is gated, and only when `category="ADMIN"` and the recipient is `HIRING_ONLY`. The 7 hiring-flow call sites (submit/resubmit/reject/each approval stage/activation, all in `app/requests_bp/routes.py`) stay on the `"HIRING"` default; the 2 Truein operational alerts (`_handle_dropped_fields`/`_notify_push_failed` in `app/integrations/truein.py`) explicitly pass `category="ADMIN"`. Any new call site must pick one of these two categories deliberately. The daily digest (`app/services/digest_email.py`, same daemon-thread pattern as `snapshot_refresh.py`, started from `create_app()`) re-reads each opted-in user's own `Notification` rows since their `last_digest_sent_at` — there's no separate queue table.

### Truein integration (`app/integrations/truein.py`)
Two live paths: `push_employee()` actually calls `addEmployeeDtls` (real push, with a 4-step field-dropping fallback chain — see the RDC Staffing Norms section below for full detail), and a separate `dry_run_to_file()` builds the same payload but never sends it, writing to `truein_dryruns/` instead (Admin → All Requests, ACTIVE requests only, SUPER_ADMIN/HEAD_HR). Full endpoint/credential/field-map reference: `Truein_API_Developer_Reference.html` in the project root (**contains live secrets — gitignored, never commit or share it**; two other files carry the same secrets verbatim and are gitignored for the same reason: `TRUEIN_API_GUIDE.html`, `Truein_API.postman_collection.json`). A parallel `ZingHR_API_Developer_Reference.html` (added 2026-09-15) covers the ZingHR side the same way, but **contains no credentials** (every example uses a placeholder you fill in from your own `.env`) — safe to track in git, not gitignored.

**Confirmed `sub_site` gap fixed 2026-09-15 (multi-company work).** `build_payload()`'s `sub_site` field was only ever populated when a `PlantDvtMapping` row existed for the selected plant — but Ultrafine/ROBO plants never have a `PlantDvtMapping` row at all (that table is RDC/DVT-specific), so `sub_site` was silently missing from every Ultrafine/ROBO Truein push, and from any DVT-unmapped RDC plant too. Fixed the same way `sitePoint` already worked: falls back to the raw plant name when no DVT reconciliation exists. Regression test: `tests/test_truein.py::test_sub_site_not_empty_when_plant_has_no_dvt_mapping_row_at_all`.

**Confirmed data-loss bug fixed 2026-09-10**: `father_name`, `reporting_manager_name` (→ Truein's `manager` field), and `uan_number` were all collected by the onboarding form but missing from `FIELD_MAP`, so `build_payload()` silently dropped them on every push. `sub_site` and `category` (cluster) were never sent at all — the form doesn't collect either directly, so they're now derived in `build_payload()` from the selected plant's `PlantDvtMapping`/`ClusterNameMapping` rows. `department` is similarly derived (fallback only) from the designation's `norm_category_id` via a new `_CATEGORY_TO_DEPARTMENT` dict — the reverse of `headcount._DEPARTMENT_TO_CATEGORY` — since new hires have no raw Department string of their own. None of this backfills already-pushed employees; it only affects pushes from this date forward.

**Confirmed mobile-number bug fixed 2026-09-10**: `push_employee()`'s pre-validation only checked "10 digits, no leading zero" before sending `mobile` — a real Indian mobile number must also start with 6-9, so a 10-digit number starting 1-5 (e.g. placeholder test data `"1234567890"`) passed our check, got sent to Truein, was rejected there, and then was mislabeled as a Truein-side rejection rather than an our-own-validation-would-have-caught-this one. Fixed by checking the leading digit too (and stripping a `+91`/`91` country-code prefix down to the bare 10 digits before sending). Separately: the old pre-check popped an invalid `mobile` from the payload with **no record anywhere** — not in `dropped_fields`, not in the notification email, not on screen — so a genuinely invalid number could vanish with zero explanation. It's now always recorded in `dropped_fields` (as `"mobile"` for our own pre-check failing, or `"mobile_truein_rejected"` for a number that passed our check but Truein rejected anyway — usually a duplicate registered to another employee — see `_DROPPED_FIELD_LABELS` in `truein.py`) so it reaches both the HR Manager notification email and the on-screen popup below.

**"Show the problem immediately" philosophy (added 2026-09-10).** When a Truein push (auto, on approval to ACTIVE — `requests_bp.approve_request()`; or manual, via `admin.truein_push()`) has a partial-drop or outright failure, the browser is redirected to the request's own detail page (`requests/detail.html`) with `?push_issue=1`, which auto-opens a `#truein-issue-modal` popup on load listing exactly which field(s) were dropped and why (or the full failure message), instead of relying only on a flash banner and a delayed HR-Manager email. The query param is stripped via `history.replaceState` right after opening so a later plain reload of the same page doesn't reopen it. This is the pattern to extend if another "something went wrong with data you can't see yet" case shows up elsewhere in the app — don't rely on email alone for anything the acting user could instead be shown on the very next page they land on.

**Pre-flight warning BEFORE the final approval, not just after (added 2026-09-10).** Beyond the after-the-fact popup above, clicking "Approve" in `requests/detail.html` now first calls `GET /requests/<token>/truein-preflight` (`requests_bp.truein_preflight()`), which re-runs `truein.preflight_check(req)` — a pure, no-network function that rebuilds the payload (`build_payload()`) and checks only what's determinable locally: `REQUIRED_TRUEIN_FIELDS` presence and mobile format (via `_clean_mobile()`, the same helper `push_employee()` itself uses — refactored out specifically so the two checks can never drift apart). If this approval wouldn't move the request to ACTIVE (checked via the pure `get_new_status()`), the endpoint returns `{"applicable": false}` and the normal approve-modal opens immediately, no extra step. If it would, and issues are found, a `#truein-preflight-modal` lists them with a "Continue to Approve" button (proceeds anyway — the existing 4-step fallback chain and post-push popup above still apply) or "Go Back" (does nothing). The frontend fails open on any fetch error — a broken pre-flight check must never block a real approval. **What this can't catch**: `sitePoint` and `manager` validity can't be exhaustively pre-verified, since Truein exposes no usable registry-lookup endpoint for either (confirmed — see "Endpoints defined but unused" in `Truein_API_Developer_Reference.html`) — but both are now constrained at the SOURCE rather than only checked after the fact, see the two entries directly below.

**The initiator's own form gets this treatment too (added 2026-09-10) — this was a real gap, not just theoretical.** `requests/form.html` already had a generic "show it immediately" mechanism for every text/tel/number field — `validateField()` runs on blur, reading each input's `pattern`/`title`/`minlength`/`maxlength` attributes and rendering an inline red error (or green "Looks good") right under the field, no page reload, no popup needed since this happens mid-form rather than at a single decision point. But the mobile field's HTML `pattern` was `[0-9]{10}` — digit count only — while the backend's real rule (`_clean_mobile()` in `truein.py`) also requires the leading digit to be 6-9. An initiator could type a fundamentally invalid number like `"1234567890"`, see a green checkmark, and only discover the mismatch much later, at pre-flight or push time. Fixed by aligning the `FieldType.TEL` branch's pattern to `[6-9][0-9]{9}` with an explicit `title` — the two rules must always match exactly, since they're independently maintained (no shared source between Python regex logic and this HTML attribute). If the backend rule in `_clean_mobile()` ever changes, update this pattern in the same commit. Regression test: `tests/test_requests.py::TestFormMobileFieldValidation`.

**`sitePoint` root-cause fix — send the known-good value, not a guess (added 2026-09-10).** Every real test push before this fix had `sitePoint` dropped by Truein. Root cause: `build_payload()` sent `sitePoint` as our own raw `plant_location` string (e.g. `"CHE- Trisulam"`), while the reconciled, Truein-verified string for the same plant already existed in `PlantDvtMapping.truein_sub_site` (e.g. `"CHE-Trisulam"`, no space) — and was already being used for the separate `sub_site` field. `sitePoint` and `sub_site` are almost certainly the same underlying Truein concept under two field names, so `build_payload()` now sends the SAME reconciled value for both — falling back to the raw plant name only when no reconciliation exists yet for that plant (unchanged behavior for that case). This doesn't require every plant to be re-mapped before hiring can proceed there; it just uses the better value whenever one is already known. Regression test: `tests/test_truein.py::TestBuildPayloadFieldCompleteness::test_site_point_uses_reconciled_truein_value_not_raw_plant_name`.

**Reporting Manager was already "pick a valid one" before this session — worth knowing this exists.** `requests/form.html`'s Reporting Manager field is a live typeahead against `GET /requests/api/truein/managers` (cache-only, real Truein employees flagged `is_manager=1`). Picking a result fills both the display name AND a hidden `l1_manager_emp_id` (a genuinely validated Truein field, unlike the deliberately-disabled `manager_emp_id` — see the FIELD_MAP note above). The form's existing "Can't continue yet" blocking-issues panel (`window.refreshBlockingIssues` in `form.html`) already flags it as a hard blocker if a name is typed but nothing was actually picked from the dropdown (`mgrNameInp.value` set, `mgrHiddenInp.value` empty) — so a free-text, unlinked manager name was never actually possible to submit. No change was needed here; this is existing behavior worth remembering next time this area comes up.

**Region (cluster) staffing page now shows every employee in the region, not just click-into-each-plant (added 2026-09-10).** `staffing_status_cluster()` already had a narrow "cluster-only staff" table (people resolved to the cluster but not to any specific plant — e.g. Accounts, Credit Control). It now also renders "Every Employee in {cluster}" — every employee resolved anywhere in the cluster, across every plant, via `headcount.get_all_employees(cluster_names={cluster_name})` (the same function backing the global "All Employees" directory), capped at `_EMPLOYEE_DIRECTORY_LIMIT` (500) with a link to the full filterable directory pre-scoped to this region (`staffing_status_employees(cluster=...)` — the route now accepts a `?cluster=` param, intersected with a Business Head's own region scoping rather than overriding it, so a BH can never widen past their own regions via the URL). The plant-level page (`staffing_status_plant.html`) already had its own full employee table — this change brings the region level up to the same standard.

**Govt ID (Aadhar) collision now caught live on the initiator's form, and the background retry loop stops on a genuine collision instead of retrying forever (added 2026-09-10, real production incident — request #32 "Barkha Patil").** Truein rejected the push with `"Govt ID already exist. Match found with GULSHAN KUMAR(...) in RDC Concrete"` — a real, permanent data collision — but this was only discovered at final-approval push time, after the initiator's request had already gone through the entire multi-step approval chain. Two independent fixes:
  1. **Live check while filling the form** — `requests_bp.check_govt_id()` (new route `POST /requests/check-govt-id`) backs `checkGovtIdDuplicate()` in `form.html`, fired `onblur` of the Aadhar field (same "show it immediately" philosophy as the mobile-pattern fix above, and the same mechanism as the pre-existing duplicate-email OTP check — see `_check_email_registered()`). `_check_govt_id_registered()` in `requests_bp/routes.py` checks (a) our own DB — any other non-deleted, non-rejected request already using this Aadhar number, and (b) Truein's warm cache only (`get_cached_employees_if_warm()`, never a live pull) via the `id_number` field. A confirmed duplicate opens `#duplicate-govtid-modal` immediately and is wired into the existing `window.refreshBlockingIssues()` "Can't continue yet" panel via a `data-govtid-dup` attribute, so the initiator can't submit past it — mirrors the pre-existing Reporting Manager blocking check. Best-effort only, same caveat as the email check: Truein's own response at push time remains the final say.
  2. **The background retry loop no longer retries an unwinnable push.** `_parse_truein_response()` now returns a `retryable` flag — `False` whenever Truein's message names a colliding employee (`"match found"`, the same reliable signal already used to distinguish a genuine collision from an idempotent "already requested" retry-of-self, see the 2026-09-04 fix above). Before this fix, `_retry_loop()` in `truein.py` retried indefinitely with exponential backoff regardless of *why* the push failed — for a genuine field collision (email/mobile/Aadhar already belongs to a different Truein employee) the identical payload will fail identically forever, so this was pure waste. Now: `push_employee()`'s result dict carries `retryable` through every fallback attempt (from `_do_push()` → `_parse_truein_response()`), and both synchronous call sites (`requests_bp.approve_request()`, `admin.truein_push()`) and the background `_retry_loop()` itself check it — a non-retryable failure sets `req.truein_retry_stopped = True` and skips `start_retry_thread()`/breaks the loop instead of scheduling another attempt. `_notify_push_failed()` takes a new `will_retry` kwarg so the HR/Admin email and the on-screen `#truein-issue-modal` (in `detail.html`, now conditioned on `req.truein_retry_stopped`) say "will NOT be retried automatically — needs manual correction" instead of the old blanket "retrying automatically" claim, which was actively misleading for this case. Regression tests: `tests/test_truein.py::TestParseTrueinResponse::test_field_collision_with_different_employee_is_not_retryable`, `tests/test_requests.py::TestGovtIdDuplicateCheck`.

**Instant client-side search on every admin config list (added 2026-09-11).** Designations, Plant Locations, Form Fields, Users, Plant/Cluster Mappings all had long, unsearchable tables (54/192/37/... rows) with no way to find one row. `render_list_search(input_id, row_selector, placeholder)` in `_macros.html` is the one shared implementation — each page calls it once and gets an identical search box wired by a single delegated `input` listener in `base.html` (`data-search-rows`/`data-search-count` attributes), filtering rows by substring match against each row's own text, live, no page reload, no per-page JS. **`plants_list()` was switched from server-side pagination to a full unpaginated list (matching every other config page)** specifically so search can find a match anywhere in the ~200 rows, not just whatever page happened to be loaded — a paginated list + client-side search would have silently only searched the current page. Add this exact macro call to any future admin list page rather than inventing a new search pattern. Regression tests: `tests/test_admin.py::TestListSearchUI`.

**Form Fields drag-to-reorder was completely broken, two stacked bugs (found and fixed 2026-09-11).** (1) SortableJS was loaded from an external CDN (`cdn.jsdelivr.net`), but the app's own CSP (`script-src 'self' 'unsafe-inline'` in `add_security_headers()`, `app/__init__.py`) blocks every external script host — the library silently failed to load (`ReferenceError: Sortable is not defined`, confirmed live in the browser console). Fixed by vendoring it locally at `app/static/js/Sortable.min.js`, loaded via `url_for('static', ...)` — satisfies the existing CSP unmodified; do not add another external CDN `<script>` anywhere in this app without either vendoring it the same way or deliberately relaxing the CSP with the stakeholder's sign-off. (2) Independently, `Sortable.create(tbody, {handle: 'tr', ...})` was backwards — SortableJS's `handle` option restricts drag-start to a DESCENDANT of each item matching that selector, and no `<tr>` ever contains a nested `<tr>`, so it matched nothing and no drag could ever start, anywhere, even with the library loading correctly. Fixed by removing `handle` entirely (the default — whole item draggable — is what the removed comment "drag the whole row" actually wanted). Confirmed live with a real mouse drag-and-drop. Regression tests (the static/config half pytest can check): `tests/test_admin.py::TestFormFieldsDragToReorder`.

**Standing policy since 2026-09-11: no external CDN/host dependency anywhere in this app — vendor everything under `app/static/`.** Triggered by the SortableJS incident directly above: the app's own CSP silently broke a real feature rather than failing loudly, which is exactly the "runtime issue" this policy exists to prevent — a third-party host being slow, down, blocked by a client network/firewall, or (as happened here) blocked by our own security headers, should never be able to break something for a user. Followed through immediately: the Inter font — the only other external dependency in the app, loaded from `fonts.googleapis.com`/`fonts.gstatic.com` on literally every page (base.html, login/forgot-password/reset-password, error pages) — was self-hosted the same day. `app/static/fonts/inter-{300,400,500,600,700,800,400-italic}.woff2` (latin subset only — deliberately dropped cyrillic/greek/vietnamese, since this is an India-only English-language app, see gotcha #14) + `app/static/css/inter-font.css` (`@font-face` rules, one file, referenced by all 6 templates via `url_for('static', ...)` — same one-shared-file principle as the search-box macro above) replace the old `<link rel="preconnect">`/Google Fonts `<link>` pair everywhere. The CSP's `style-src`/`font-src` no longer allow `fonts.googleapis.com`/`fonts.gstatic.com` at all — tightened, not just left permissive-but-unused. **When adding any future external library or asset (JS, CSS, font, icon set, ...): download it into `app/static/` and reference it via `url_for('static', ...)` — do not add a `<script src="https://...">`/`<link href="https://...">` pointing at an external host.** If a case genuinely needs a live external call (an API integration, not a static asset), that's a different, deliberate decision — this policy is about assets that could just as easily ship with the app. Regression tests: `tests/test_admin.py::TestNoExternalCdnDependency`.

### Testing
Tests use in-memory SQLite — no MySQL required. CSRF is disabled. Each test gets a per-function DB transaction that rolls back after the test. User factory fixtures (`initiator`, `business_head`, `hr_manager`, etc.) are in `tests/conftest.py`.

## RDC Staffing Norms Hiring Gate

Gates RDC-company hiring requests by production-volume-based staffing norms: compares current headcount (reconciled from ZingHR + Truein) against volume-derived allowed headcount (from the Daily Volume Tracker, a separate app) per plant/cluster/role, blocking or allowing new-hire submissions accordingly. A read-only dashboard surfaces the same data to HR Manager/Head HR/Dr. Bhoon/Admin. **This entire gate — volume-based restriction, DVT reconciliation, the classification formulas below — stays RDC-only, unchanged by the 2026-09-15 multi-company work** (see the "Multi-Company Support" section further down): Ultrafine and Robo Silicon get their own, much simpler, ungated headcount view instead of being folded into this pipeline. Gotcha #7 below covers how ZingHR's shared tenant is filtered for *this* RDC-only gate specifically.

**Classification model (redesigned 2026-08-20):** existing-employee role-bucketing is now driven **entirely by an employee's raw Department value**, not designation. `headcount._classify_by_department()` maps Department straight onto 6 plant-scope categories: **Plant Manager** (`PI/API/Acting PI`), **Technical** (`Technical`/`Techinical`/`Plant & Technical`, plus `Trainee Civil` once tenure > 90 days — this category absorbed the old separate "FTs/LT/TO" formula, so its `allowed_headcount` is now the SUM of two `NormRequirement` rows per tier), **Batchers/Production Officer** (`Batching`), **Materials** (`Material`/`Materials`), **Assistant** (`Assistant/RMX` incl. space-around-slash variants), **Operations** (`Operations`, ungated/visibility-only — no formula). Everything else stays unclassified. The old designation-based `ExternalDesignationMapping` admin-mapping workflow and the entirely separate Technical/Non-Technical split (`ZingHrDepartmentClassification`/`TechnicalHeadcountSnapshot`) were **fully removed** — do not reintroduce them; the department rule above is the sole source of truth for current headcount, for both the dashboard and the live gate. New-hire gating still uses `Designation.norm_category_id` (admin-set per designation at `/admin/designations`) since a new hire has no Department yet — a separate, unrelated mapping.

**Critical operational gotchas — read before touching this system, each cost real time to discover:**

1. **ZingHR/Truein caches are per-process module globals** (`_employees_cache` in each integration module). Not shared across processes. Every fresh server process starts with a COLD Truein cache, requiring a full ~7-8 minute paginated pull (rate-limited ~1 req/10-15s, paced at 50s in code) before `truein.get_cached_employees_if_warm()` returns anything. A standalone diagnostic script (`python -c "..."`) gets its OWN cold cache too — never assume it sees the running server's warm cache.

2. **`create_app()` unconditionally starts the background snapshot-refresh thread.** Every throwaway script that calls `create_app()` spawns a competing thread that races for the MySQL advisory lock and does its own live Truein pull. **Never call `create_app()` in a one-off diagnostic script** — use a raw `sqlalchemy.create_engine(os.environ['DATABASE_URL'])` connection for read-only DB checks instead.

3. **The snapshot-refresh MySQL advisory lock must use one dedicated connection**, not `db.session`. `_compute_and_store_snapshot()` commits partway through, which can return `db.session`'s underlying connection to the pool — if `GET_LOCK`/`RELEASE_LOCK` ride on `db.session.execute()`, the release can land on a *different* physical connection than the one that acquired it, silently failing to release and orphaning the lock (symptom: refreshes permanently report "another refresh is already in progress" with no actual process running). Fixed via `conn = db.engine.connect()` held open for the whole critical section in `compute_and_store_snapshot()`.

4. **ZingHR returns some `employeeCode`s twice** — one copy with a full `attributes[]` array, one with it empty/missing. `zinghr._dedupe_by_employee_code()` keeps the fuller copy. Always call through `_fetch_all_employees_raw()`, never bypass it.

5. **Face-attendance-device pseudo-employees** exist in both sources (e.g. `empId="FACEBACHUPALLY"`, name `"Face HYD Bachupally"`) — filtered via `headcount._is_face_device()` (checks both code and name; ~5% of ZingHR ones only have "face" in the code, not the name).

6. **Truein's `getEmployeeDtls` has no status filter** — returns every record it has ever seen (~60% inactive in practice). Filtered client-side to `status == "active"`. ZingHR *is* filtered server-side via the `employmentstatus: "Active"` request parameter.

7. **ZingHR is one shared tenant across RDC, Robo Silicon, and Ultrafine** — no server-side company filter exists. For *this RDC gate's* computation, `headcount.py` excludes confirmed non-RDC `Company` attribute values client-side; blank/missing Company is kept (can't confirm it's not RDC). **Since 2026-09-15, Robo/Ultrafine's excluded records are no longer just discarded** — a separate function consumes exactly those same two `Company` values for the Multi-Company headcount view (see that section below); this RDC pipeline's exclusion logic and the other one's inclusion logic must stay exact inverses of each other (`_NON_RDC_COMPANIES` / `_ZINGHR_COMPANY_TO_CODE` in `headcount.py`).

8. **Other exclusions applied in `headcount.py`**: `site_name` must be exactly `"RDC Concrete"` (excludes the separate `"RDC Drivers"` site); Truein `category` junk values (`on roll`/`onroll`/`other`/`1st`/`2nd`, case-insensitive); `Location`/`sub_site` exactly `"Head Office"` (case-insensitive) excluded on both sources.

9. **Truein field semantics are not obvious from their names**: `sub_site` = plant-level location (→ `PlantDvtMapping.truein_sub_site`), `category` = cluster-level location (→ `ClusterNameMapping.truein_category`). `sub_site` values are inconsistent in practice — sometimes a real plant name, sometimes a short code like `"HY1"` — matching is fuzzy-text based and will miss code-style values.

10. **Existing-employee classification is Department-only now (redesigned 2026-08-20) — do not reintroduce a separate designation-based or Technical/Non-Technical path.** `headcount._classify_by_department()` normalizes the raw Department string (case/whitespace, slash-spacing) and looks it up in `_DEPARTMENT_TO_CATEGORY`. **Truein DOES carry a real `department` field** (confirmed 2026-08-19 against live data — it's populated for ~44% of active Truein records and shares most of its vocabulary with ZingHR's Department values verbatim, e.g. `"Trainee Civil"`, `"Technical"`, `"Batching"`, plus a `"Plant & Technical"` variant not seen on ZingHR). `"Trainee Civil"` only counts toward Technical once tenure exceeds 90 days (parsed from `date_of_joining`, which is ZingHR's `"18 Aug 2025"` format on one source and Truein's ISO `"2025-08-16"` on the other — `_parse_join_date()` tries both); an unparseable/missing date is treated as "not yet 3 months" (excluded), not guessed. Values that don't match any of the 6 categories (Sales & Marketing, Accounts, Logistics, HSE, Trainee Non Civil, ...) are simply unclassified — not an error, not shown anywhere. **One designation-aware exception, added 2026-08-21 after a confirmed bug at MH- Chh. Sambhaji Nagar**: `"Trainee Engineer"` is a superset that includes Trainee Civil — a trainee sitting under a Technical-looking department OTHER than literally `"Trainee Civil"` (e.g. `"Plant & Technical"`, `"Technical"` itself) must NOT count toward Technical via the direct department mapping, only via the Trainee Civil + >90-day path above. `_classify_by_department()` takes `designation` as a parameter specifically for this check (`_TECHNICAL_DEPARTMENT_VALUES` + `"trainee" in designation.lower()`) — this is a narrow, confirmed-by-data exception to "Department-only," not a reopening of the old designation-based system; it only ever *excludes* a trainee from the direct Technical mapping, never adds anyone via designation. Does not affect trainees in other departments (e.g. Trainee RMX Technician under Assistant/RMX still counts immediately).

11. **`NormRoleCategory.is_capacity_gated`** (default `True`) is `False` only for `Operations` now — visibility-only, never blocked by production volume. Every other active plant category (Plant Manager, Technical, Batchers/Production Officer, Materials, Assistant) is volume-gated (confirmed with stakeholder). `Sales`/`Customer Relations`/`Security` were retired (soft-deleted) in the 2026-08-20 redesign, not just left ungated.

12. **A `NormRequirement`-fetching query must never assume one row per (tier, category).** Technical has two rows per plant tier (its own fixed formula plus the merged former-FTs/LT/TO rate/fixed formula) — `headcount.py`'s `requirement_by_tier_cat` is a `dict[str, list]`, and `staffing_norms.sum_allowed_headcount()` sums a list, not `compute_allowed_headcount()` on a single `.first()` row. A `.first()`/single-dict-value query here will silently drop one of Technical's two formulas.

13. **DVT (Daily Volume Tracker, a separate app) is the source of truth for plant/cluster identity**; ZingHR + Truein are the source of truth for employee data. Plant reconciliation happens via `PlantDvtMapping` (admin-editable at `/admin/plant-mappings`, never overwrites a row an admin already hand-corrected). The same DVT `plant_code` appearing on two `PlantDvtMapping` rows always means the same physical plant (confirmed with stakeholder) — see "Known open items" for the merge mechanism. **`auto_match_plants()` is deliberately exact-match-only, not fuzzy (redesigned 2026-08-20, confirmed with stakeholder)** — a candidate name (from `PlantLocation` ∪ Truein `sub_site` ∪ ZingHR `Location`, all cache-only reads except ZingHR's 1h-TTL cache which it blocks on) must exactly equal (after `_normalize()`) DVT's `erp_name` or `daily_tracker_name`; nothing in between. `matched_on` records which of the two fields won (`'erp_name'` / `'tracker_name'`), NULL for MANUAL/UNMATCHED rows. A row whose candidate name disappears entirely from this run's inputs is still swept and reset (see the function's stale-`AUTO_FUZZY` cleanup pass) rather than left stuck on a stale match. Fuzzy matching was removed here specifically because it risks silently pointing two genuinely different plants at the same DVT code (see the Coimbatore/Greater Noida/etc. groups below) — that risk doesn't apply to `auto_match_clusters()`, which still fuzzy-matches (clusters are coarser-grained and a wrong cluster match is much lower-stakes than a wrong plant match).

14. **All timestamps are stored naive-UTC**; displayed in IST via the `| ist` Jinja filter (`app/__init__.py::_format_ist`). Never call `.strftime()` directly on a stored datetime in a template — it'll show UTC, which is wrong for this India-only app.

15. **`plant_location_name` and `alias_name` are `utf8mb4_unicode_ci` in MySQL — case-INSENSITIVE unique constraints**, confirmed the hard way 2026-08-21 (`"Head Office"` vs `"Head office"` collide as the same value; inserting the second throws `IntegrityError`, not silently succeeding as a second row). `auto_match_plants()` and `apply_manual_plant_mapping.py` both key their in-memory dicts by `.lower()` for this reason — a naive exact-Python-string dict here will eventually throw a duplicate-key error in production once two sources disagree on casing for the same real plant name (this happened for real: adding ZingHR `Location` as a third candidate source in `_our_plant_names()` immediately produced 10 same-plant-different-casing collisions, e.g. `"GUJ-Vapi"` vs `"GUJ- Vapi"`). Also: `plant_location_name` has a DB-level UNIQUE constraint that doesn't care about `is_deleted` either — a soft-deleted row (e.g. from `merge_duplicate_plants.py`) still occupies its name and must be looked up and reused, never blindly re-inserted.

16. **The onboarding form's Plant Location dropdown is sourced from `PlantDvtMapping`, not a live Truein call (changed 2026-08-21).** `requests_bp._dvt_matched_plant_options()` / `GET /requests/api/plant-locations` return only plants with a confirmed DVT mapping (`dvt_plant_code IS NOT NULL`, i.e. `AUTO_EXACT` or `MANUAL`) — an initiator can never submit a plant name the staffing gate can't resolve. Dropdown `value` stays `plant_location_name` (what the gate/snapshot/every other lookup joins on); the visible label is DVT's `daily_tracker_name` (falling back to `plant_location_name` if blank). The old `/requests/api/truein/sites` endpoint and `truein.fetch_site_points()` were removed — that endpoint actually read Truein's `category` field, which is the CLUSTER-level field (see gotcha #9), not plant-level, so it was already a latent mismatch even before this change.

17. **`NormTier` ranges for the same (scope, sheet) must never overlap — a real risk, not theoretical, confirmed 2026-09-21.** Both `staffing_norms._find_tier()` and `headcount.py`'s own copy of the same logic scan `NormTier` rows with **no `ORDER BY`** and return the **first** row whose `[min_value, max_value)` contains the value — two tiers with overlapping ranges resolve to whichever row MySQL happens to return first, which is unspecified. This was nearly introduced when a 4th, lower "< 1500 m³" PLANT/SHEET1 tier was added (see "Plant staffing norms tier update" below): the old "< 3000 m³" tier had `min_value=NULL`, so it silently overlapped the new "< 1500 m³" tier for every volume under 1500. Fixed by narrowing "< 3000 m³" to `min_value=1500` (relabeled "1500-3000 m³") in the same migration that added the new tier — `add_lt1500_tier.py` does both in one script, deliberately, not as two separate changes. Any future tier insertion between two existing brackets must do the same: narrow the tier immediately above so every bracket stays a true non-overlapping partition. Regression tests: `tests/test_staffing_norms.py::TestAdjacentTierBoundaries`.

**Plant staffing norms tier update (2026-09-21):** the stakeholder's "Staffing Norms for Plants" spreadsheet changed to add a **4th, lower volume bracket** — plants averaging under 1500 m³/month over the last 3 months now get their own tier ("< 1500 m³"), sitting below the existing "< 3000 m³" (now "1500-3000 m³", see gotcha #17), "3000-5000 m³", and "> 5000 m³" tiers. **Every value in the 3 pre-existing tiers is unchanged** — this was confirmed cell-by-cell against the new spreadsheet image, not assumed; only the new bracket's own requirement values are new data: Plant Manager 1, Technical 1 (+2 for the merged former-FTs/LT/TO formula, same "two rows summed" convention as every other tier — see gotcha #12), Batchers/Production Officer 1, Materials 1, Assistant 1, Customer Relations Nil, Sales 2, Security 2 (the last 3 categories are soft-deleted/retired per gotcha #11 and not read by the live gate, but got requirement rows anyway for consistency with how the other 3 tiers still carry theirs). `add_lt1500_tier.py` (project root, idempotent, same one-off-migration convention as `migrate_staffing_categories.py`) applies this: inserts the new tier + its 9 requirement rows, and narrows "< 3000 m³"'s `min_value` from `NULL` to `1500`. **Run once against the live DB**, same convention as every other root-level migration script here — do not rerun `seed_staffing_norms.py` to pick this up (see the note on that script above, it would blow away the whole current category structure).

## Multi-Company Support (RDC / Ultrafine / ROBO)

**Added 2026-09-15.** The onboarding form's Company Code dropdown always had all three companies seeded (`seed.py`), but the *live* DB only had RDC's `FormFieldOption` active — so in practice only RDC was ever selectable. All three are now usable. The RDC Staffing Norms hiring gate (previous section) stays entirely RDC-only, untouched — Ultrafine/ROBO get a separate, much simpler path with no production-volume gating at all, not folded into that pipeline.

**What changed, by model:**
- `COMPANY_CHOICES = ["RDC", "Ultrafine", "ROBO"]` — new module-level constant in `app/models.py`, plain strings (matches `OnboardingRequest.company_code`'s existing convention, not an enum).
- `PlantLocation.company` — new `String(20)`, default `"RDC"`. Plants are now company-scoped; `/admin/plants` has a company selector alongside its existing Active/Disabled tabs, and the add/edit plant form has a Company dropdown.
- `EmployeeLocationSnapshot.company` — new nullable `String(20)`. RDC rows **never** set this (stay `NULL`) — only the new Ultrafine/ROBO snapshot path (below) sets it. Every RDC read-side query (`get_employees_at_plant`, `get_employees_at_cluster`, `get_all_employees`, and anything else reading this table for RDC) **must** filter `EmployeeLocationSnapshot.company.is_(None)` or Ultrafine/ROBO employees will leak into RDC-only views now that the table is shared — this was a real bug found and fixed before it ever shipped (see below).

**Onboarding form (`requests/form.html`) and API:** `GET /requests/api/plant-locations` now accepts `?company=` (default `"RDC"`). RDC keeps its existing `_dvt_matched_plant_options()` path (region/cluster picker, DVT-reconciled). Ultrafine/ROBO use a new `_company_plant_options(company)` in `requests_bp/routes.py` — a flat, unpaginated list of that company's active `PlantLocation` rows, no DVT, no cluster grouping. The form's Plant Location picker collapses to a flat dropdown (no cluster level) whenever every returned option's `cluster` is `null`, and re-fetches/clears its selection on Company Code change.

**Staffing Status page is now 3 tabs** (`requests_bp.staffing_status()` / `staffing_status.html`) — RDC tab is the pre-existing page, byte-for-byte unchanged (region/cluster drill-down, production-volume gating). Ultrafine/ROBO tabs are new and deliberately simple: one row per that company's active `PlantLocation` showing current headcount only, no allowed-headcount/gating column (there is none), clicking through to `staffing_status_company_plant.html` for the employee list at that plant.

**The Ultrafine/ROBO headcount snapshot — `_compute_and_store_other_company_snapshot()` in `app/services/headcount.py` — is ZingHR-only, deliberately, not an oversight.** Unlike the RDC pipeline (which reconciles both ZingHR and Truein), this function pulls only `zinghr.fetch_active_employees()`. This was verified, not assumed: on 2026-09-15 the entire raw Truein dataset was pulled live (all 7,610 records, every status, every site — not just the app's normal RDC-filtered subset) and grouped by `site_name`. Result: exactly two values exist on this Truein account, `"RDC Concrete"` (1,967) and `"RDC Drivers"` (5,643) — nothing else. Robo/Ultrafine are simply not tracked in Truein under this account/subscription; there is nothing there to reconcile against. If this ever needs reconfirming (e.g. after a Truein account/plan change), rerun `truein._fetch_all_employees_raw()` (full pull, ~7-8 min, see gotcha #1) and check `Counter(e.get("site_name") for e in raw)`.

**`_ZINGHR_COMPANY_TO_CODE`** (`headcount.py`, right after `_compute_and_store_snapshot()`) is the exact inverse of the RDC pipeline's `_NON_RDC_COMPANIES` exclusion set (gotcha #7 above) — `{"robo silicon pvt. ltd.": "ROBO", "ultrafine mineral and admixtures pvt ltd": "Ultrafine"}`. Plant resolution is a simple normalized-name exact match (`_normalize_name()` — case/hyphen/whitespace-insensitive) between the employee's ZingHR `Location` and a company-scoped `PlantLocation.name` — no DVT, no `PlantNameAlias`-style alias table (doesn't exist for non-RDC companies), no fuzzy fallback. **This means each distinct raw `Location` string needs its own matching `PlantLocation` row** — if the same physical plant is recorded as two different Location strings (e.g. `"Girmapur-Plant"` vs `"Sales-Girmapur"`), that employee only resolves under whichever exact string is entered as a plant name; there's currently no mechanism to alias the two together.

**Shared-timestamp pattern (critical, caused a real bug caught before shipping):** every RDC read-side helper finds "the latest run" via a table-wide `MAX(computed_at)` across the whole `EmployeeLocationSnapshot` table, company-agnostic. If the Ultrafine/ROBO snapshot generated its own independent, later timestamp in the same refresh cycle, `MAX(computed_at)` would silently resolve to the *other* company's run and every RDC query would return empty. Fixed by having `compute_and_store_snapshot()`'s wrapper capture the RDC pass's own resulting timestamp and pass it explicitly into `_compute_and_store_other_company_snapshot(now=...)` — both passes always share one exact timestamp, same MySQL advisory-lock critical section, same 2-hourly refresh cadence. Regression tests: `tests/test_headcount.py::TestSharedTimestampAndCompanyIsolation`.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
